## 2. 必须更正的错误陈述

### A1. "整场归零时自动跳过反问直接交卷" —— **事实错误**

**【事实】** 设计文档 3.7 节写了这条，但核查确认：
- 后端**不存在**任何"整场时间归零 → 自动结算"的路径（grep `remaining <= 0`、`scheduler`、`cron` 均无业务命中，仅有邮件/JWT 的过期逻辑）。
- 前端**同样不存在**该逻辑（`grep remainingSeconds.value <= 0` 无命中）。

**【事实】** 实际后果：
1. 进入 `phase=REVERSE` 后，若用户直接关闭页面 → 面试**永久停在 `IN_PROGRESS`**，无报告、无清扫任务。
2. 这个状态**不是我新引入的**（原来停在"未答完最后一题"也一样，无自动终止），但**我的改动扩大了出现面**：改造前答完最后一题必得报告；改造后答完还要再点一次「交卷」或「跳过反问」。

**【观点】** 这是我这次改造中最应该主动报告却没报告的行为变化。修法见 §7-⑥。

**【事实】处理状态（2026-10-13）**：设计文档 `题库设计方案-v2.md` §3.7 中那条虚构的"整场归零时自动跳过反问直接交卷（沿用现有自动结算路径）"**已更正**为陈述实际行为与后果，并在 §7.9 遗留/风险里挂上这条缺口。代码层的自动收尾**仍未实现**——三选一属 §8-D6，等你决策。

**【事实】A1 自身的更正（2026-10-13 本轮，D6 实施时逐行读代码发现）**：上面"前端**同样不存在**该逻辑"这一句是**我的复核失误**。`InterviewSession.vue` 一直有 `watch(remainingSeconds)` 的归零收尾分支（未答完时自动交卷、一题未答时自动中止），它的判据写成 `if (val > 0) return`，我用 `remainingSeconds.value <= 0` 去 grep 自然搜不到——**用"我以为的写法"去搜代码，等于没搜**。因此：
- 「后端没有整场归零的结算入口」仍成立（这条路径依赖前端计时器活着）；
- 「关页面 → 永久 `IN_PROGRESS`」仍成立，且正是这条真实缺口让 D6 的 (a) 前端归零自动 finish 变成"依赖一个用户可能不会守着的计时器"，不如 (b) 后端清扫可靠。

**【事实】D6 落地（2026-10-13）**：按你的决定「倒计时改为计时器 + 保留后端清扫」执行——`duration_minutes` 退化为预计时长，服务端下发 `elapsed_seconds` 正计时，前端顶部显示「已用」，**上述归零分支连同 `autoFinished` 一起删除**（"归零"状态不再存在）；新增 `app/services/interview_sweeper.py`，由 `main.py` 的 lifespan 起 asyncio 轮询（默认 600 秒一轮、静默 24 小时判定，环境变量可调），把 `IN_PROGRESS`/`PAUSED` 僵尸场次收尾：有评分 → `force` 结算出报告，一题未答 → `CANCELLED`。回归：`test_zombie_sweeper_settles_answered_and_cancels_empty` 覆盖三态，`test_interview_has_no_hard_deadline_anymore` 覆盖"远超预计时长仍可作答"。

### A5. `test_reliability.py` 实际降低了一处契约强度

| 场景 | 改造前行为 | 改造后行为 |
|---|---|---|
| 报告生成失败 | `/answer` 返回 **200** + `report_state=FAILED`（**优雅降级**） | `/finish` 抛异常 → **500**（测试用 `pytest.raises` 包住） |

**【事实】** 这是**真实的契约退化**：前端 `doFinish()` 调 `/finish` 时拿不到结构化失败信息，只能提示通用错误，丢失了"报告生成失败，可重试"的语义。

**【事实】处理状态（2026-10-13）**：已按 §7-② 修复。`/finish` 内 `try/except` 包住 `finalize_interview`，失败返回 `200 + {report_id: null, report_state: "FAILED", retryable: true, message}`（4xx 业务拒绝仍按原状态码抛出，避免把"未答完/并发占用"混成报告失败）；前端 `doFinish()` 按 `report_id` 是否为空决定提示重试或跳转报告页；`test_reliability.py` 对应断言已由 `pytest.raises` 改为断言结构化降级。

## 3. 我引入、但未充分暴露的风险

### B1. 反问端点缺少幂等与并发保护（设计缺失）

**【事实】**
- 反问表 `interview_reverse_questions` 的 `unique_constraints` 为空，`(interview_id, seq)` **无唯一约束**。
- `submit_reverse_question_core` 用 `count()` 推导 `seq`：并发两次提交会各自读到 `existing=0`，插入两条 `seq=1`。
- 前端仅有 `:loading` 防连点；**网络超时重发、刷新后重提仍会重复**。

**【事实】** 而逐题作答有 `request_id` 幂等 + 租约 CAS 保护。**反问完全没有对应机制。**

**【观点】** 这直接对应你原始需求里的"重复提交处理"一条，属于我这一轮做得不到位的地方。

**【事实】处理状态（2026-10-13）**：已按 §7-① 落地。`ReverseSubmitRequest` 增加必填 `request_id`；服务端按 `(interview_id, request_id)` 重放（原样重发返回既有结果且不重复调用 LLM，同 `request_id` 换内容 409，缺字段 422）；`seq` 改由 `max(seq)+1` 推导并在提交冲突时捕获 `IntegrityError`；迁移 `0011` 加列 + 先清洗历史 `(interview_id, seq)` 重复行 + 建 `uq_reverse_interview_seq`、`uq_reverse_interview_request` 两个唯一索引；前端 `submitReverse` 用 `sessionStorage` 记住最近一次 `{text, request_id}`，覆盖"超时重发"和"刷新后原样重提"两种重复路径。**仍未验证**：真实网络双发的端到端行为（当前由唯一索引在数据库层兜底，验证方式是 pytest 内的并发用例，非线上抓包）。

### B2. `aliases` 覆盖不全导致的匹配行为不一致

**【事实】** 163 题有别名、134 题没有（构成见 §1）。

**【推测】** 后果是：同一技能，在本次补过的题上走"别名归一化匹配"，在未补的旧题上只能走子串匹配。表现为**组卷结果在同一技能内部出现难解释的差异**（例如"消息队列"能命中 `skill_name=Kafka` 的新题，但命中不了旧题）。

### B3. 关联大类是硬编码白名单，且无回归保护

**【事实】** `paper_builder.py` 的 `RELATED_CATEGORIES` 仅登记 3 条：`全栈研发→后端/前端`、`运维架构↔系统运维`。

**【推测】** 新增岗位大类时不会报错，只会静默让该大类专业题全部落到 AI 生成。**【事实】** 目前没有任何测试用例守着这张白名单。

**【观点】** 相当于把"无约束的跨类兜底"改成了"有约束的跨类"，但**约束本身没有回归保护**。

### B4. 方向上的自我回退（我认为这一条最值得你注意）

**【观点】** 在 P0-1 我把"**取消跨大类兜底**"讲成核心修复；到 P0-3 又通过 `RELATED_CATEGORIES` **加回了受控的跨类**。

**【观点】** 我用"显式白名单、只登记技能重叠的大类"合理化了这个回退，但**没有认真评估"直接补题"是否更干净**——全栈研发补 12 题、运维两类各补 6 题，规模并不大，与已补的 179 题相比是零头。

**【观点】** 这可能是**我选了改动小的路，而不是更对的路**。这一点需要你判断（见 §8-D2）。

**【事实】** 因此：**297 这个数字是硬验证过的（数据库实测），但这 179 道题的"质量"是零验证的**——难度标签由我自评、`reference_points` 由我自拟、无同行评审、无查重、无用户反馈。

**【观点】** 闸门对设计有效、对我无效，这在流程上是自相矛盾的。

### E1. "反问是否计入总分"可能是伪二选一

**【推测】** 依据：按当前设计（完全不计分 + 「跳过反问，直接交卷」按钮位于主视觉左侧、是更省事的路径），我预计**多数用户会直接跳过**。

## 14. 第三轮：D1 口径再收紧——反问省掉 AI 回答（2026-10-13）

**你的决定**：D1 的"零成本"不只是不计分，还要**把 AI 回答那次 LLM 调用省掉**。

**我的执行口径**：反问环节变成**纯记录**——候选人提交提问即同步落库，AI 既不作答也不点评，报告只把提问列成清单。没有采用"改成模板化回答"的折中，因为那仍是把编造文本当作真实回答存进记录，与全站"禁止假数据"原则冲突；而且保留回答就必须保留 `ai_response NOT NULL` 这条列，链路上就还得留着 LLM 调用。

### 14.4 本轮的代价与新增建议

- 反问不再有任何"回应"，环节价值完全落在候选人自己身上。**这使得「反问提示卡」的性价比显著上升**：每大类 3~5 条静态提问方向（设计文档 §7 早已挂着、至今未实现），既能填补"没有回应"的空白，又是零 LLM 成本的数据。若你要做，我建议做成 `question_bank` 的 `REVERSE_HINT` 类题目或独立小表，面试间按岗位大类直接渲染。
