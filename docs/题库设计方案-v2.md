# 题库与组卷设计方案 v2（含反问环节）

> 状态：**P0（1/2/3）、P1（1/2）全部实施完毕**；P2 仅剩「`aliases` 回填」与「语言配置 / 内容安全」等可选增强。
> 范围：题库数据模型与内容扩充、组卷匹配算法修正、模拟面试反问环节。
> 关联现状：`backend/app/data/question_bank.py`（118 题种子）、`backend/app/services/paper_builder.py`（组卷引擎）、`backend/app/services/interview_core.py`（答题/推进/结算）、`frontend/src/views/personal/InterviewSession.vue`（面试间）。

## 一、现状诊断

### 1.1 题库覆盖度（实测统计，共 118 题）

| 岗位大类 | 题数 | 问题 |
|---|---|---|
| 后端开发 | 21 | 相对充足，但部分技能仅 1 题（Kafka/分布式事务/JVM/Netty/ES/Spring Cloud 各 1） |
| 前端开发 | 8 | TypeScript/Node.js/CSS/工程化/浏览器原理 各 1 |
| 人工智能 / 大数据 | 8 / 6 | 每技能仅 1 题 |
| 系统运维 / 运维架构 / 质量保障 / 客户端 / 系统底层 / 信息安全 | 3~4 | 每技能仅 1 题 |
| 8 个非技术岗（产品/运营/销售/HR/财务/市场/设计/客户成功） | 各 4 | 只够 5 题综合卷（专业 3），10 题卷必缺 |
| 通用 | 24 | GENERAL 12 + STRESS 12 |

### 1.2 组卷引擎缺陷清单（不贴切题目的根因）

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| D1 | **跨大类兜底**：本大类专业题不足时，tier2「不限大类」直接抽其他岗位的题 | `build_paper` 的 `tiers = [[category, GENERIC], None]` | 大数据 10 题技术卷（需专业 7）只有 6 题存量 → 冒出 Java 并发题 |
| D2 | **跨题型借用**同样不限大类 | `build_paper` 补足段 | 同上，且题型口径混乱 |
| D3 | AI 兜底生成几乎不触发：tier2 让题库"永远够"，缺口 `missing` 恒为空 | 同上 | 本该由 AI 按 JD+简历定制生成的题，被跨岗位的陈题顶替 |
| D4 | 技能匹配靠子串（`j in s or s in j`），无别名机制 | `_skill_hit_rank` | "Java并发"能命中"Java"属侥幸；"消息队列"命中不了"Kafka" |
| D5 | `stage` 字段不参与组卷，整卷 `random.shuffle` | `_pick` / `build_paper` | 题序与真实面试脱节（上来系统设计、最后才专业基础） |
| D6 | 自适应追问要求"同技能 + 不同难度"，但多数技能仅 1 题 | `interview_core._maybe_followup` | 除后端少数技能外，FOLLOW_UP/DEEP/BASIC 基本失效 |
| D7 | `Job.skills_required` 默认值是 Java 技术栈 | `models/job.py` | 非技术岗若未显式填技能，匹配基准就是错的 |
| D8 | 难度只来自用户手选，与岗位经验要求无关 | `create_interview` | 1-3 年岗位可被组出满卷 HARD |

### 1.3 流程缺口

最后一题提交后 `submit_answer_core` 直接置 `COMPLETED` 并结算报告，没有真实面试标配的**反问环节**（"你有什么想问我的吗？"）。

## 二、题库 v2 设计

### 2.1 数据模型变更（`question_bank` 表）

新增/调整字段（Alembic 迁移，均可空、向后兼容）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `aliases` | String(255) | 技能别名，逗号分隔。如 `Java并发` 题填 `Java,多线程,并发,JUC`；匹配时技能名与别名做归一化交集，替代 D4 的子串判断 |
| `min_experience` / `max_experience` | String(20) | 适用经验段（如 `1-3年`、`5年以上`），用于 D8 的难度锚定 |
| `review_status` | String(20) | `APPROVED`（种子/人工已审）/ `PENDING`（AI 生成待审）。**组卷只取 APPROVED**，防止未审 AI 题回流污染 |
| `quality_score` | Float, 可空 | 由历史作答反馈聚合（该题平均得分异常低/高、被跳过率高时预警），供管理端排序治理 |

不变项：`job_category / question_type / skill_name / stage / difficulty / reference_points_json / enabled / usage_count` 沿用；`source` 枚举增加 `SEED_V2`。

### 2.2 覆盖度目标（内容扩充矩阵）

**核心原则：每个技能至少 EASY/MEDIUM/HARD 各 1 题**（否则 D6 追问失效），每个大类专业题存量 ≥ 最大常规卷的专业题需求。

| 层级 | 目标 | 说明 |
|---|---|---|
| P0（先行）**已完成** | 后端 21→39、前端 8→19、人工智能 8→**27**、大数据 6→**18**（新增 60 题，总量 118→178） | 按「每技能至少 EASY/MEDIUM/HARD 各 1 题」逐技能精确补齐；实际数量高于原先的整数估计（AI/大数据 原估偏低，以实测缺口为准） |
| 关联大类（**替代新增题**） | `全栈研发` 复用「后端开发 + 前端开发」；`运维架构` ⇄ `系统运维` 互为补充 | 这些大类题库为空或极小（3 题）且技能高度重叠：复用比新造题更省成本，也更贴合岗位实际 |
| P1 **已完成** | 8 个非技术大类各 4→12（新增 65 题，总量 178→243） | 保证 10 题卷（综合模式专业 5）不跨类；其中 4 个技能原题即为 HARD，补的是 EASY+MEDIUM |
| P2 **已完成** | 运维/测试/客户端/底层/安全 6 类共 3~4→9~12（新增 40 题） | 长尾补齐，每技能三档难度齐全 |
| 通用池 **已完成** | GENERAL 12→20、STRESS 12→20（新增 16 题） | 高频复用，跨岗位中性；压力题补入非技术向场景（薪资谈判、上级不合规要求、客户强硬改期等） |
| 反问提示卡 | 每大类 3~5 条「高质量反问方向」 | 存 `question_bank`（`question_type=REVERSE_HINT`）或独立小表，供反问环节展示参考提示 |

总量目标：118 → 约 320 题。种子仍走幂等灌库脚本（并入 seed_demo 的既有模式），新题 `source=SEED_V2` 不被重建覆盖。

扩充来源：人工撰写为主；AI 按 JD 批量生成的题走 `source=AI_GENERATED + review_status=PENDING`，管理端（`views/admin/QuestionBank.vue`）审核通过后才可入卷——形成"生成→审核→入库"闭环。

### 2.3 组卷匹配算法 v2（修复 D1~D5、D7~D8）

抽题规则修订如下，**优先级从上到下**：

1. **相关性下限（修 D1/D2/D3）**：
   - PROFESSIONAL 题只允许两级候选：① 本岗位大类 → ② `RELATED_CATEGORIES` 登记的关联大类（`全栈研发 → 后端开发/前端开发`；`运维架构` ⇄ `系统运维`）。**取消"不限大类"兜底与跨题型借用**；关联大类是受控白名单，不是原来的乱取。
   - 仍不足时计入 `missing`，交由 AI 按 JD + 简历上下文生成（生成题必须带 `skill_name ∈ 岗位技能`、参考答案要点，`source=AI_GENERATED`，卷面快照记录）。
   - GENERAL / STRESS 维持现状（本就是"通用"大类）。
2. **技能匹配升级（修 D4）**：`岗位技能 ∩ (skill_name ∪ aliases)` 归一化（小写、去空格）后非空即 rank0；`综合素养/抗压能力` 仍为 rank1；其余 rank2。
3. **阶段有序组卷（修 D5）**：整卷不再全 shuffle，按真实面试节奏排布：
   `开场通用（自我介绍类）→ 专业基础 → 深度探究 → 项目深挖 → 系统设计 → 压力应对`，同阶段内随机。`stage` 排序权重做成常量表，管理端可见。
4. **难度锚定（修 D8）**：用户未显式选难度时，由 `Job.experience` 推导基准（1-3年→EASY/MEDIUM 为主，3-5年→MEDIUM，5年以上→MEDIUM/HARD），显式选择仍优先。
5. **技能默认值治理（修 D7）**：组卷时若岗位无 `JobSkill` 且 `skills_required` 等于建表默认值，视为"无技能信号"，专业题 rank 全部按同大类 rank2 处理并倾向 AI 生成，而不是错误地命中 Java 题。
6. 卷面快照 `paper_json` 增加 `relevance_floor=true`、`stage_order`、AI 补足明细，保证可追溯。

### 2.4 治理与观测

- 管理端题库页新增**覆盖度看板**：大类 × 题型 × 难度 × 技能计数矩阵，红格标注"单技能 <3 题"与"大类存量 < 10 题"。
- 组卷日志：每次开考记录"命中 rank / AI 补足数 / 缺口"，一周内某大类 AI 补足率 >30% 即提示需补题。

## 三、反问环节设计（REVERSE Phase）

### 3.1 目标流程

```
逐题作答(QA) ──最后一题提交──▶ 反问环节(REVERSE) ──提交提问/跳过──▶ 交卷结算(COMPLETED) ──▶ 报告
                                    │ 候选人最多记 3 条提问，AI 面试官不作答（零成本）
                                    │ 可随时"跳过反问，直接交卷"
                                    └ 整场不设截止，仅累计「已用」时长
```

与真实面试一致点：面试官主动发起（"我的问题完了，你有什么想问我的吗？"）、候选人可婉拒、提问计入面试记录与报告。
差别在于本系统是模拟面试：没有真人招聘方在场，所以反问定位是**帮候选人把想问的问题整理成清单**（可原样带到真实面试现场），而不是让 AI 扮演面试官作答。

### 3.2 数据模型

- `Interview` 新增 `phase` 列：`QA`（默认）/ `REVERSE` / `DONE`。状态机不动（仍 IN_PROGRESS），phase 只做环节标记，避免波及现有 start/pause/resume/abort 迁移。
- 新表 `interview_reverse_questions`：

| 字段 | 说明 |
|---|---|
| `interview_id` / `seq` | 归属面试、第几条反问（1~3） |
| `request_id` | 客户端幂等键（与逐题作答同款约定），历史行为空 |
| `candidate_text` | 候选人的反问内容 |
| `created_at` | |

  原设计另有 `ai_response`（扮演式回答）与 `evaluation_json`（反问质量点评）两列，D1 定稿"零成本"后由迁移 `0013_reverse_record_only` 删除——只要保留这两列，链路就必须产出回答文本，而无 Key 时的 mock 兜底会把编造的面试官回答写进记录。

  唯一索引 `uq_reverse_interview_seq(interview_id, seq)` 与 `uq_reverse_interview_request(interview_id, request_id)`：反问曾既无幂等也无约束，`seq` 由 `count()` 推导，并发提交或超时重发会插入两条 `seq=1`（自查报告 B1），故补索引作为最后防线；采用唯一索引而非表级约束，是为了在 SQLite 上无需整表重建。
- `InterviewReport` 新增 `reverse_summary_json`（可空）：`questions[{seq, candidate_text}]` + `question_count` + `skipped` + `comment`（只陈述记录到的条数，不含对提问质量的评价）。

### 3.3 API 设计（`api/v1/interviews.py`）

| 端点 | 行为 |
|---|---|
| `GET /interviews/{id}/reverse` | 返回 phase、已记录的提问列表、剩余额度 |
| `POST /interviews/{id}/reverse` | 记录 1 条反问（**必须带 `request_id`**）→ 同步写入 `interview_reverse_questions`，**不调用 LLM**；同一 `request_id` 原样重发直接回读既有结果，同 `request_id` 换内容 409，缺字段 422；超 3 条 422；phase≠REVERSE 时 409 |
| `POST /interviews/{id}/reverse/skip` | 跳过，等价于允许 finish |
| `POST /interviews/{id}/finish` | 放宽：最后一题已答完即可结算（不再要求先 COMPLETED）；phase 置 DONE；**报告生成失败时优雅降级**为 `200 + {report_id: null, report_state: "FAILED", retryable: true}`，作答与评分保留，可再次交卷重试（4xx 业务拒绝仍按原状态码返回） |

`submit_answer_core` 改动点：最后一题（`next_q is None`）时不再直接 `COMPLETED`，改为 `phase=REVERSE` 并返回 `{"finished_qa": true, "phase": "REVERSE"}`；用户走"结束面试"对话框仍可强制立即交卷（保持现有 Esc/取消交互不变）。

### 3.4 反问零成本定稿（D1 已决策并落地：2026-10-13）

- **零成本的三层含义**：不计分（不进 6 维 Rubric、不产生能力画像证据）、不占时（整场不设截止、反问无单题限时）、**不调用 AI**（不消耗 token、不等生成）。
- 因此删除 `AIProvider.answer_reverse_question` 及其 `ReverseAnswerSchema`：原实现每条提问都要等一次 LLM 往返，且无 Key 时落到 mock 兜底文案——那等于把编造的"面试官回答"写进面试记录，与"禁止假数据"原则冲突。
- 真实面试里反问的对象是招聘方，本系统没有真人可答（真人参与属 §六 范围外），所以把环节价值定位回"整理你想问的问题"，回答留给真实面试现场。
- 保留的约束：`request_id` 幂等、`(interview_id, seq)` 与 `(interview_id, request_id)` 唯一索引、最多 3 条、非 REVERSE 环节 409。

### 3.5 评分与报告接入

- 反问**不进 6 维 Rubric 加权**（避免变相惩罚内向用户），但：
  - 报告新增「反问环节记录」区块：候选人提问清单（逐条原文）；
  - `comment` 只陈述"本环节不评分、不耗时，记录到 N 个问题，可原样带到真实面试"，不评价提问质量；
  - 完全跳过反问时，报告温和提示"真实面试中反问是展示动机的重要窗口"。
- 能力分闭环（UserCompetency）不消费反问数据。

### 3.6 前端交互（`InterviewSession.vue`）

- 最后一题提交后，主区切换为反问卡片：面试官引导语 → 输入框（复用现有文本+语音口述链路）→ 提交后即时回显为「你问」清单 → "再记一条（≤3）/ 跳过反问，交卷"。
- 开场文案明确"AI 面试官不作答、不评分，也不消耗你的时间"，避免用户期待回答。
- 顶部进度由 `第 x/N 题` 变为 `反问环节`；结束面试对话框逻辑不变（phase=REVERSE 时"交卷并生成报告"始终可用，替代原"需至少作答 1 题"的禁用条件之一）。
- 提交反问的请求不再需要为 LLM 等待放宽超时（此前 `api/index.ts` 给了 120 秒），已回到全局默认超时。
- 报告页（`InterviewReportView.vue`）反问区块只展示提问清单。

### 3.7 计时与边界（D6 已决策并落地：2026-10-13）

- **整场不限制提交时间**：`duration_minutes` 退化为「预计时长」，只用于开场文案展示，不再参与任何截止判定。服务端改下发正计时的 `elapsed_seconds`（`interview_core.get_elapsed_seconds`，以 `started_at` 为准、暂停期间冻结），面试间顶部由「剩余 mm:ss」改为「已用 mm:ss」，开场提示新增一条「本场不设硬性截止时间」。
- **逐题建议限时保留**：单题 `time_limit_sec` 仍由服务端按 `current_question_shown_at` 判定超时并轻扣分（每 30 秒 3 分、上限 15 分、不归零）；反问环节不设单题限时。
- **二次更正（我的复核失误，必须记录）**：自查报告 A1 与本文上一版都断言"前端同样没有归零收尾分支"——这是错的。`InterviewSession.vue` 一直存在 `watch(remainingSeconds)` 的「归零自动交卷 / 一题未答自动中止」逻辑，判据写作 `if (val > 0) return`，用 `remainingSeconds <= 0` 去 grep 自然搜不到。D6 把整场改正计时后，"归零"这一状态不再存在，该 watch 与 `autoFinished` 标记一并删除，因此这条路径不是被修复而是被**取消**。
- **僵尸会话兜底（D6-2）**：`app/services/interview_sweeper.py` 由 `main.py` 的 lifespan 启动后台轮询任务（默认每 600 秒一轮，`INTERVIEW_SWEEP_INTERVAL_SECONDS` 可调），把连续静默超过 `INTERVIEW_ZOMBIE_IDLE_HOURS`（默认 24 小时，按最后一次作答/反问时间判定，而不是 `started_at`）的 `IN_PROGRESS`/`PAUSED` 会话收尾：已有评分的 `force` 结算出报告（不让已写的回答白答），一题未答的置 `CANCELLED`；单轮上限 50 场，结算失败则回滚留到下一轮重试。因此"关页面导致的僵尸场次"从无人处理变为最迟 24 小时兜底。
- 暂停/恢复：phase 保持；恢复时把 `started_at` 与单题锚点整体前移暂停时长，故正计时与单题用时都不含暂停。
- 薄弱题重练（`purpose=RETRAIN`）与取消面试（abort）行为不变。
- 企业正式面试（ENTERPRISE_RECRUITMENT）同样进入反问环节；清扫遇到"报告必须 REAL 来源"的 503 时不写终态，下一轮再试。

## 四、迁移与实施顺序（供后续排期，本阶段不写码）

1. **M1 组卷修正**（收益最大、改动最小）：paper_builder 相关性下限 + 别名匹配 + 阶段排序 + 难度锚定；`aliases/min_experience/review_status` 迁移；AI 补足路径打通。
2. **M2 题库扩充**：P0 技术大类补齐 → P1 非技术 → P2 长尾；管理端覆盖度看板与 AI 题审核流。
3. **M3 反问环节**：phase 列 + 新表迁移 → provider 方法 → 3 个端点 → 前端面试间/报告页。
4. 每步回归基线：`tests/test_question_bank.py`（44 项）+ 面试冒烟；新增用例覆盖"跨类零容忍、AI 补足、反问全流程"。

## 五、验收标准

- 任选 19 个大类各开一场 10 题综合卷：**专业题 100% 来自本大类或 AI 按 JD 生成**，不再出现跨岗位陈题。（D2 取消 `RELATED_CATEGORIES` 借题白名单后这条才真正成立——此前全栈研发、系统运维、运维架构三类是靠借后端/前端/互借凑数的。）
- 每技能 ≥3 难度题后，FOLLOW_UP/DEEP/BASIC 追问在抽查中可实际触发。

### 7.8 P1-1：开场环节（已完成）

### 7.10 P1-3：整场计时改造 + 僵尸会话清扫（D6，已完成）

**决策**：将倒计时改为计时器，不限制模拟面试的提交时间；同时保留自查报告 §8-D6 选项 (b) 的后端定时清扫兜底。

**设计要点**
- **接口契约更名而非兼容堆叠**：`remaining_seconds` → `elapsed_seconds`（`InterviewOut`、`AnswerEvaluationOut`、`/start`、`/resume`、WS `connected`/`state` 帧一起改），不留双字段。历史幂等回放里的旧 `result_json` 缺 `elapsed_seconds`，端点用 `result.get(...)` 读取，避免 KeyError。
- **`duration_minutes` 语义降级**：仍落库、仍展示（开场文案「预计 N 分钟」），但不再参与任何截止判定；单题 `time_limit_sec` 与超时轻扣分保持原样。
- **清扫判定用「最后活动时间」而不是 `started_at`**：不限制提交时间后，一场合法面试可以跑很久，只有连续静默超阈值才是僵尸。活动标记取 `created_at / started_at / paused_at` 与最后一条作答、最后一条反问时间的最大值。
- **收尾分两档**：已有评分 → `finalize_interview(force=True)` 出报告（不让已写的回答白答）；一题未答 → `CANCELLED`（此时结算必 409）。失败一律回滚并留到下一轮重试，避免企业面试因"报告必须 REAL 来源"的 503 被误写终态。
- **不引入新依赖**：用 FastAPI `lifespan` 起一个 `asyncio` 轮询任务（默认 600 秒一轮，单轮上限 50 场），阈值与周期走环境变量；`TestClient(app)` 不进入 lifespan，因此回归不会被后台任务干扰。

### 7.12 P1-2 收尾：反问改为纯记录（D1 定稿第二轮），已完成

**决策口径**：D1 的"零成本"从"不计分、不占时"进一步覆盖到 **不调用 AI**——每条提问不再触发一次 LLM 往返，反问环节只登记候选人的提问本身。

**为什么这样收**
- 模拟面试没有真人招聘方在场（§六 明确列为范围外），AI 扮演的"面试官回答"本质是生成文本：无 Key 时走 mock 兜底，等于把写死的模板话术当作真实回答存进面试记录，与全站"禁止假数据"原则冲突。
- 一次 LLM 往返带来 token 成本与数秒等待，而它对成绩、能力画像、报告结论都不产生任何输入——`reverse_summary` 只用于展示。移除后反问提交变成同步落库，前端也不再需要为它放宽到 120 秒超时。
- 反问对候选人的真实价值在"你有没有想问的问题"，因此把它定位成**可带到真实面试现场的提问清单**。

**改动文件**
- `backend/app/services/interview_core.py`：`submit_reverse_question_core` 由 `async` 改同步，删除 `ai_context` + `answer_reverse_question` 调用与 `jd_text`/问答摘要上下文构造（连带去掉回答为空的 503 分支）；`seq` 推导抽为 `_next_reverse_seq`；`_reverse_state` 的 `questions` 只剩 `{seq, candidate_text}`；`reverse_summary` 键名 `answered_count` → `question_count`，`comment` 由"表现良好/具备信息增量"这类无依据评价改为陈述记录到的条数。
