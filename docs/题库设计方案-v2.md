# 题库与组卷设计方案 v2（含反问环节）

> 状态：**P0（1/2/3）、P1（1/2）全部实施完毕**；P2 仅剩「`aliases` 回填」与「语言配置 / 内容安全」等可选增强。
> 范围：题库数据模型与内容扩充、组卷匹配算法修正、模拟面试反问环节。
> 关联现状：`backend/app/data/question_bank.py`（118 题种子）、`backend/app/services/paper_builder.py`（组卷引擎）、`backend/app/services/interview_core.py`（答题/推进/结算）、`frontend/src/views/personal/InterviewSession.vue`（面试间）。

---

## 一、现状诊断

### 1.1 题库覆盖度（实测统计，共 118 题）

| 岗位大类 | 题数 | 问题 |
|---|---|---|
| 后端开发 | 21 | 相对充足，但部分技能仅 1 题（Kafka/分布式事务/JVM/Netty/ES/Spring Cloud 各 1） |
| 前端开发 | 8 | TypeScript/Node.js/CSS/工程化/浏览器原理 各 1 |
| 人工智能 / 大数据 | 8 / 6 | 每技能仅 1 题 |
| 系统运维 / 运维架构 / 质量保障 / 客户端 / 系统底层 / 信息安全 | 3~4 | 每技能仅 1 题 |
| 8 个非技术岗（产品/运营/销售/HR/财务/市场/设计/客户成功） | 各 4 | 只够 5 题综合卷（专业 3），10 题卷必缺 |
| 通用 | 24 | GENERAL 12 + STRESS 12 |

### 1.2 组卷引擎缺陷清单（不贴切题目的根因）

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| D1 | **跨大类兜底**：本大类专业题不足时，tier2「不限大类」直接抽其他岗位的题 | `build_paper` 的 `tiers = [[category, GENERIC], None]` | 大数据 10 题技术卷（需专业 7）只有 6 题存量 → 冒出 Java 并发题 |
| D2 | **跨题型借用**同样不限大类 | `build_paper` 补足段 | 同上，且题型口径混乱 |
| D3 | AI 兜底生成几乎不触发：tier2 让题库"永远够"，缺口 `missing` 恒为空 | 同上 | 本该由 AI 按 JD+简历定制生成的题，被跨岗位的陈题顶替 |
| D4 | 技能匹配靠子串（`j in s or s in j`），无别名机制 | `_skill_hit_rank` | "Java并发"能命中"Java"属侥幸；"消息队列"命中不了"Kafka" |
| D5 | `stage` 字段不参与组卷，整卷 `random.shuffle` | `_pick` / `build_paper` | 题序与真实面试脱节（上来系统设计、最后才专业基础） |
| D6 | 自适应追问要求"同技能 + 不同难度"，但多数技能仅 1 题 | `interview_core._maybe_followup` | 除后端少数技能外，FOLLOW_UP/DEEP/BASIC 基本失效 |
| D7 | `Job.skills_required` 默认值是 Java 技术栈 | `models/job.py` | 非技术岗若未显式填技能，匹配基准就是错的 |
| D8 | 难度只来自用户手选，与岗位经验要求无关 | `create_interview` | 1-3 年岗位可被组出满卷 HARD |

### 1.3 流程缺口

最后一题提交后 `submit_answer_core` 直接置 `COMPLETED` 并结算报告，没有真实面试标配的**反问环节**（"你有什么想问我的吗？"）。

## 二、题库 v2 设计

### 2.1 数据模型变更（`question_bank` 表）

新增/调整字段（Alembic 迁移，均可空、向后兼容）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `aliases` | String(255) | 技能别名，逗号分隔。如 `Java并发` 题填 `Java,多线程,并发,JUC`；匹配时技能名与别名做归一化交集，替代 D4 的子串判断 |
| `min_experience` / `max_experience` | String(20) | 适用经验段（如 `1-3年`、`5年以上`），用于 D8 的难度锚定 |
| `review_status` | String(20) | `APPROVED`（种子/人工已审）/ `PENDING`（AI 生成待审）。**组卷只取 APPROVED**，防止未审 AI 题回流污染 |
| `quality_score` | Float, 可空 | 由历史作答反馈聚合（该题平均得分异常低/高、被跳过率高时预警），供管理端排序治理 |

不变项：`job_category / question_type / skill_name / stage / difficulty / reference_points_json / enabled / usage_count` 沿用；`source` 枚举增加 `SEED_V2`。

### 2.2 覆盖度目标（内容扩充矩阵）

**核心原则：每个技能至少 EASY/MEDIUM/HARD 各 1 题**（否则 D6 追问失效），每个大类专业题存量 ≥ 最大常规卷的专业题需求。

| 层级 | 目标 | 说明 |
|---|---|---|
| P0（先行）**已完成** | 后端 21→39、前端 8→19、人工智能 8→**27**、大数据 6→**18**（新增 60 题，总量 118→178） | 按「每技能至少 EASY/MEDIUM/HARD 各 1 题」逐技能精确补齐；实际数量高于原先的整数估计（AI/大数据 原估偏低，以实测缺口为准） |
| 关联大类（**替代新增题**） | `全栈研发` 复用「后端开发 + 前端开发」；`运维架构` ⇄ `系统运维` 互为补充 | 这些大类题库为空或极小（3 题）且技能高度重叠：复用比新造题更省成本，也更贴合岗位实际 |
| P1 **已完成** | 8 个非技术大类各 4→12（新增 65 题，总量 178→243） | 保证 10 题卷（综合模式专业 5）不跨类；其中 4 个技能原题即为 HARD，补的是 EASY+MEDIUM |
| P2 **已完成** | 运维/测试/客户端/底层/安全 6 类共 3~4→9~12（新增 40 题） | 长尾补齐，每技能三档难度齐全 |
| 通用池 **已完成** | GENERAL 12→20、STRESS 12→20（新增 16 题） | 高频复用，跨岗位中性；压力题补入非技术向场景（薪资谈判、上级不合规要求、客户强硬改期等） |
| 反问提示卡 | 每大类 3~5 条「高质量反问方向」 | 存 `question_bank`（`question_type=REVERSE_HINT`）或独立小表，供反问环节展示参考提示 |

总量目标：118 → 约 320 题。种子仍走幂等灌库脚本（并入 seed_demo 的既有模式），新题 `source=SEED_V2` 不被重建覆盖。

扩充来源：人工撰写为主；AI 按 JD 批量生成的题走 `source=AI_GENERATED + review_status=PENDING`，管理端（`views/admin/QuestionBank.vue`）审核通过后才可入卷——形成"生成→审核→入库"闭环。

### 2.3 组卷匹配算法 v2（修复 D1~D5、D7~D8）

抽题规则修订如下，**优先级从上到下**：

1. **相关性下限（修 D1/D2/D3）**：
   - PROFESSIONAL 题只允许两级候选：① 本岗位大类 → ② `RELATED_CATEGORIES` 登记的关联大类（`全栈研发 → 后端开发/前端开发`；`运维架构` ⇄ `系统运维`）。**取消"不限大类"兜底与跨题型借用**；关联大类是受控白名单，不是原来的乱取。
   - 仍不足时计入 `missing`，交由 AI 按 JD + 简历上下文生成（生成题必须带 `skill_name ∈ 岗位技能`、参考答案要点，`source=AI_GENERATED`，卷面快照记录）。
   - GENERAL / STRESS 维持现状（本就是"通用"大类）。
2. **技能匹配升级（修 D4）**：`岗位技能 ∩ (skill_name ∪ aliases)` 归一化（小写、去空格）后非空即 rank0；`综合素养/抗压能力` 仍为 rank1；其余 rank2。
3. **阶段有序组卷（修 D5）**：整卷不再全 shuffle，按真实面试节奏排布：
   `开场通用（自我介绍类）→ 专业基础 → 深度探究 → 项目深挖 → 系统设计 → 压力应对`，同阶段内随机。`stage` 排序权重做成常量表，管理端可见。
4. **难度锚定（修 D8）**：用户未显式选难度时，由 `Job.experience` 推导基准（1-3年→EASY/MEDIUM 为主，3-5年→MEDIUM，5年以上→MEDIUM/HARD），显式选择仍优先。
5. **技能默认值治理（修 D7）**：组卷时若岗位无 `JobSkill` 且 `skills_required` 等于建表默认值，视为"无技能信号"，专业题 rank 全部按同大类 rank2 处理并倾向 AI 生成，而不是错误地命中 Java 题。
6. 卷面快照 `paper_json` 增加 `relevance_floor=true`、`stage_order`、AI 补足明细，保证可追溯。

### 2.4 治理与观测

- 管理端题库页新增**覆盖度看板**：大类 × 题型 × 难度 × 技能计数矩阵，红格标注"单技能 <3 题"与"大类存量 < 10 题"。
- 组卷日志：每次开考记录"命中 rank / AI 补足数 / 缺口"，一周内某大类 AI 补足率 >30% 即提示需补题。

## 三、反问环节设计（REVERSE Phase）

### 3.1 目标流程

```
逐题作答(QA) ──最后一题提交──▶ 反问环节(REVERSE) ──提交反问/跳过──▶ 交卷结算(COMPLETED) ──▶ 报告
                                    │ 候选人最多提 3 个问题，AI 面试官逐条回答
                                    │ 可随时"跳过反问，直接交卷"
                                    └ 整场 duration_minutes 继续计时（反问建议预留 3~5 分钟）
```

与真实面试一致点：面试官主动发起（"我的问题完了，你有什么想问我的吗？"）、候选人可婉拒、问答计入面试记录与报告。

### 3.2 数据模型

- `Interview` 新增 `phase` 列：`QA`（默认）/ `REVERSE` / `DONE`。状态机不动（仍 IN_PROGRESS），phase 只做环节标记，避免波及现有 start/pause/resume/abort 迁移。
- 新表 `interview_reverse_questions`：

| 字段 | 说明 |
|---|---|
| `interview_id` / `seq` | 归属面试、第几条反问（1~3） |
| `candidate_text` | 候选人的反问内容 |
| `ai_response` | AI 面试官的扮演式回答 |
| `evaluation_json` | 反问质量点评（动机/思考深度/岗位匹配信号），**只作报告素材，不计入总分** |
| `created_at` | |

- `InterviewReport` 新增 `reverse_summary_json`（可空）：反问问答列表 + 综合点评。

### 3.3 API 设计（`api/v1/interviews.py`）

| 端点 | 行为 |
|---|---|
| `GET /interviews/{id}/reverse` | 返回 phase、已进行反问列表、剩余条数、该大类"反问提示卡" |
| `POST /interviews/{id}/reverse` | 提交 1 条反问 → `ai_provider.answer_reverse_question()` 生成回答与点评；超 3 条 422；phase≠REVERSE 时 409 |
| `POST /interviews/{id}/reverse/skip` | 跳过，等价于允许 finish |
| `POST /interviews/{id}/finish` | 放宽：最后一题已答完即可结算（不再要求先 COMPLETED）；phase 置 DONE |

`submit_answer_core` 改动点：最后一题（`next_q is None`）时不再直接 `COMPLETED`，改为 `phase=REVERSE` 并返回 `{"finished_qa": true, "phase": "REVERSE"}`；用户走"结束面试"对话框仍可强制立即交卷（保持现有 Esc/取消交互不变）。

### 3.4 AI 面试官回答策略（`ai/provider.py` 新增方法）

- 输入：岗位 JD、公司公开信息（名称/行业）、本场问答摘要、候选人反问文本。
- 约束：以面试官第一人称扮演；回答**克制、真实**（2~5 句）；对薪资福利、未公开业务细节一律以"这个我们 HR 环节会详细聊/不方便透露"式话术回避，不编造具体数字；回答后不反问候选人（保持环节边界）。
- 点评维度（不影响总分）：问题是否体现对岗位/团队/成长的关注、是否有信息增量、与 JD 匹配度；输出 1 段评语 + 1~2 条"下次可以怎么问"的建议。
- Mock provider 同步实现兜底文案，保证无 AI 密钥时流程可走通（与现有评分链路的 RULE/UNKNOWN 机制一致）。

### 3.5 评分与报告接入

- 反问质量**不进 6 维 Rubric 加权**（避免变相惩罚内向用户），但：
  - 报告新增「反问环节表现」区块：问答全文 + 点评 + 建议；
  - 完全跳过反问时，报告温和提示"真实面试中反问是展示动机的重要窗口"。
- 能力分闭环（UserCompetency）不消费反问数据。

### 3.6 前端交互（`InterviewSession.vue`）

- 最后一题提交后，主区切换为反问卡片：面试官引导语 → 输入框（复用现有文本+语音口述链路）→ 提交后气泡展示 AI 回答 → "再问一条（≤3）/ 跳过反问，交卷"。
- 顶部进度由 `第 x/N 题` 变为 `反问环节`；结束面试对话框逻辑不变（phase=REVERSE 时"交卷并生成报告"始终可用，替代原"需至少作答 1 题"的禁用条件之一）。
- 报告页（`InterviewReportView.vue`）新增反问问答折叠区。

### 3.7 计时与边界

- 反问不设单题倒计时，只受整场 `duration_minutes` 约束；整场归零时自动跳过反问直接交卷（沿用现有自动结算路径）。
- 暂停/恢复：phase 保持，暂停时长剔除逻辑复用 `paused_at`。
- 薄弱题重练（`purpose=RETRAIN`）与取消面试（abort）行为不变。
- 企业正式面试（ENTERPRISE_RECRUITMENT）同样进入反问环节（AI 扮演），后续真实招聘方接入真人回答划为范围外。

## 四、迁移与实施顺序（供后续排期，本阶段不写码）

1. **M1 组卷修正**（收益最大、改动最小）：paper_builder 相关性下限 + 别名匹配 + 阶段排序 + 难度锚定；`aliases/min_experience/review_status` 迁移；AI 补足路径打通。
2. **M2 题库扩充**：P0 技术大类补齐 → P1 非技术 → P2 长尾；管理端覆盖度看板与 AI 题审核流。
3. **M3 反问环节**：phase 列 + 新表迁移 → provider 方法 → 3 个端点 → 前端面试间/报告页。
4. 每步回归基线：`tests/test_question_bank.py`（44 项）+ 面试冒烟；新增用例覆盖"跨类零容忍、AI 补足、反问全流程"。

## 五、验收标准

- 任选 19 个大类各开一场 10 题综合卷：**专业题 100% 来自本大类或 AI 按 JD 生成**，不再出现跨岗位陈题。
- 每技能 ≥3 难度题后，FOLLOW_UP/DEEP/BASIC 追问在抽查中可实际触发。
- 模拟面试完整走通：逐题 → 反问（提问/被答/跳过三路径）→ 交卷 → 报告含反问表现区块。
- 历史面试记录、卷面快照、错题重练不受影响（旧数据 phase 默认 QA，报告无 `reverse_summary_json` 时前端隐藏区块）。

## 六、范围外

- 真人招聘方参与反问、反问环节语音链路专项优化、题库多语言、岗位大类体系重构（维持 19 类）。

## 七、实施记录

### 7.1 已锁定的决策（2026-10-12 确认）

| 项 | 决策 | 理由 |
|---|---|---|
| 题库扩充方式 | 由开发方直接撰写种子（离线、零 API 成本），入库即 `APPROVED`；另留 5~10 题走 `PENDING→审核` 试点 | `reference_points` 是评分锚点，质量决定评分准确性，不宜赌 LLM；同时小范围验证审核流产品能力 |
| 基线失败项（alembic 断言过期） | 改为与 alembic `head` 动态比较 | 硬编码版本号的写法每次新增迁移都会过期 |
| 开场环节 | 纳入范围，用固定引导语模板（不调 LLM） | 与反问共用 `phase` 机制，边际成本≈0；真实面试必经环节 |
| WS 流式输出 | 不做，保持 REST | 后端 WS 骨架虽已完备，但前端接入需处理重连/心跳与双通道一致性，属体验优化而非功能缺口 |

### 7.2 P0-1：组卷相关性下限（已完成）

**改动文件**
- `backend/app/models/question.py`：`QuestionBank` 新增 `aliases`（技能别名，逗号分隔）与 `review_status`（`APPROVED`/`PENDING`）。
- `backend/alembic/versions/0008_question_bank_relevance.py`：守卫式加列（沿用 0002 的 `Base.metadata.create_all` + 逐列存在性判断风格），既有 118 条题目默认 `APPROVED`。
- `backend/app/services/paper_builder.py`：
  - 新增 `RELATED_CATEGORIES` 白名单（`全栈研发 → 后端开发/前端开发`；`运维架构` ⇄ `系统运维`）与 `_candidate_tiers()`：专业题为本类 → 关联大类，通用/压力题维持「本类+通用 → 不限大类」。
  - **移除跨题型借用段**：它按候选池顺序补位、不看岗位大类，是跨岗位陈题的来源之一。
  - `_skill_hit_rank()` 改为「技能名 + aliases 归一化 token 集合」匹配，保留包含匹配以兼容无别名的历史题目。
  - `build_paper()` 取题仅限 `enabled=True AND review_status='APPROVED'`。
- `backend/app/api/v1/interviews.py::create_interview`：题库缺口按缺失题型逐类交 AI 生成（此前题型被写死为 `PROFESSIONAL`）。
- `backend/scripts/seed_question_bank.py`：灌库 payload 支持 `aliases`（为 P0-3 铺路）。

**验证结果**

| 产品经理 / COMPREHENSIVE / 10 题 | 9 | 4（全为产品经理） | `{PROFESSIONAL: 1}` | 0 |
| 后端开发 / COMPREHENSIVE / 10 题 | 10 | 5（全为后端开发） | 无 | 0 |
| 全栈研发 / TECHNICAL / 5 题 | 5 | 4（后端 3 + 前端 1） | 无 | 0 |
| 全栈研发 / COMPREHENSIVE / 10 题 | 10 | 5（后端 3 + 前端 2） | 无 | 0 |
| 运维架构 / TECHNICAL / 10 题 | 9 | 6（运维架构 3 + 系统运维 3） | `{PROFESSIONAL: 1}` | 0 |

### 7.8 P1-1：开场环节（已完成）

**设计要点**
- `Interview.phase` 只做**环节标记**（`OPENING`/`QA`/`REVERSE`/`DONE`），**完全不参与状态机**：`start/pause/resume/abort` 的合法性判断仍由 `status` 决定，故既有 409 拦截与双通道（REST/WS）行为零改动。
- 开场引导语用**前端固定模板**渲染（岗位名、题量、时长由接口数据填充），**不调用 LLM**——零成本、零延迟、文案可控。
- 开场由「点击开始面试」关闭：前端在 `phase=OPENING` 时**不再自动调用 start**（原先 `loadSession` 见到 READY 就自动 start），后端在 `start` 时把 `phase` 从 `OPENING` 推进为 `QA`。
- 迁移把既有 26 条会话**回填为 `QA`**（而非 `OPENING`）：它们早已越过开场，默认成 OPENING 会让旧记录重开时突然冒出开场卡片，属于行为突变。

**改动文件**
- `backend/app/models/interview.py`：新增 `phase`（默认 `OPENING`）。
- `backend/alembic/versions/0009_interview_phase.py`：守卫式加列，既有行 `server_default="QA"`。
- `backend/app/schemas/interview.py`：`InterviewOut.phase`（默认 `QA`，向后兼容）。
- `backend/app/services/interview_core.py::transition_interview`：`start` 时若 `phase=OPENING` 则推进为 `QA`（**仅 OPENING 时推进**，避免从 `PAUSED` 恢复时把反问环节打回 QA）。
- `backend/app/api/v1/interviews.py::build_interview_out`：下发 `phase`。
- `frontend/src/views/personal/InterviewSession.vue`：开场卡片（引导语 + 面试须知 + 开始按钮）；`isOpening` 为真时隐藏题序/计时/作答区/底部控制栏，并跳过计时与摄像头初始化。

### 7.9 P1-2：反问环节（已完成）

**设计要点**
- **逐题作答结束不再自动结算**：`submit_answer_core` 在最后一题后把 `phase` 置为 `REVERSE`，`status` 保持 `IN_PROGRESS`（故状态机与 409 拦截逻辑不变），由「跳过反问」或「交卷」收尾。
- **反问分表存储**：`interview_reverse_questions` 与 `InterviewQuestion/Answer` 分离，反问问答**不进 rubric 总分**，只作为报告的「反问环节表现」素材，避免变相惩罚内向型候选人。
- **同题型兜底思路复用到 AI 层**：`AIProvider.answer_reverse_question` 内置 mock 兜底文案，无 Key 时反问流程仍可走通；提示词硬约束「薪资福利/未公开信息一律回避、不编造数字、不反问候选人」。
- 上限 **3 条**（`MAX_REVERSE_QUESTIONS`），超限 422、非反问环节调用 409。
